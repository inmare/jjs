# Qwen3-VL: 이미지 크기와 비전 토큰(근사)

이 문서는 **Qwen3-VL 계열**이 이미지를 넣을 때 쓰는 **`smart_resize` 규칙**과, 이 저장소 **`vendor/`에 두는 공식 Qwen3VL-4B GGUF + mmproj** 를 llama.cpp로 돌릴 때 흔한 **픽셀 상·하한**을 기준으로 한 **토큰(근사)** 정리입니다.

## 이 프로젝트에서 말하는「vendor」

| 파일 | 예시 경로 |
|------|-----------|
| LLM GGUF | `vendor/qwen3-vl-4b-q8-gguf/Qwen3VL-4B-Instruct-Q8_0.gguf` |
| mmproj | `vendor/qwen3-vl-4b-q8-gguf/mmproj-Qwen3VL-4B-Instruct-Q8_0.gguf` |

llama-server 기동 시 로그에 나오는 `load_hparams: image_min_pixels`, `image_max_pixels` 가 실제 런타임 기준입니다.  
다른 변종 GGUF는 숫자가 다를 수 있으니, **항상 로그로 한 번 확인**하는 것이 안전합니다.

## 핵심만: 경계는「가로·세로 각각」이 아니라「면적」

- **정렬**: 가로·세로는 **32픽셀 배수**가 되도록 맞춤 (`patch_size=16` × `merge_size=2`).
- **하한 `min_pixels`**: (32 격자로 맞춘 뒤) **면적이 `min_pixels` 미만**이면 **비율 유지로 확대**.
- **상한 `max_pixels`**: **면적이 `max_pixels` 초과**면 **비율 유지로 축소**.
- 그 사이면 비율은 거의 유지하고, **32배수 맞추느라** 해상도가 조금 바뀔 수 있음.

공식 구현: [Qwen3-VL `vision_process.py` 의 `smart_resize`](https://github.com/QwenLM/Qwen3-VL/blob/main/qwen-vl-utils/src/qwen_vl_utils/vision_process.py)

## 비전 토큰(근사) 공식

리사이즈 후 \((H', W')\)에 대해:

\[
\text{비전 토큰} \approx \frac{H' \times W'}{1024}
\]

( \(1024 = (16 \times 2)^2\) , 즉 **factor = 32** 의 제곱.)

HF의 `<|image_pad|>` 개수 등과 **완전 일치**는 아닐 수 있으나, **픽셀 예산·리사이즈 여부**를 가늠하기엔 보통 충분합니다.

## 프리셋별 픽셀·토큰 상한 (짧은 비교표)

| 프리셋 | 용도 | `min_pixels` | `max_pixels` | 토큰(근사) 범위 |
|--------|------|----------------|----------------|------------------|
| **`vendor`** (이 repo 기본) | `vendor/` Qwen3VL-4B mmproj + llama.cpp 에 흔한 메타 | 8,192 | 4,194,304 | **약 8 ~ 4,096** |
| `hf-4b` | Hugging Face `Qwen3-VL-4B-Instruct` preprocessor | 65,536 | 16,777,216 | **약 64 ~ 16,384** |
| `utils` | qwen-vl-utils 코드 기본 상수 | 4,096 | 16,777,216 | **약 4 ~ 16,384** |

**vendor** 에서 한 장이 쓸 수 있는 비전 토큰 상한은 대략 **4,096** (면적 상한 **4,194,304** 픽셀, 예: **2048×2048** 근처)입니다.

## 짧은 표: 해상도 예시 → 리사이즈 후 → 토큰 (`vendor` 프리셋)

아래는 저장소의 `qwen3_vl_image_tokens.py --preset vendor` 와 동일한 계산입니다.

| 입력 (W×H) | smart_resize 후 (W×H) | 면적 (px) | 비전 토큰 (근사) |
|------------|------------------------|-----------|------------------|
| 100×100 | 96×96 | 9,216 | 9 |
| 256×256 | 256×256 | 65,536 | 64 |
| 320×320 | 320×320 | 102,400 | 100 |
| 512×512 | 512×512 | 262,144 | 256 |
| 640×640 | 640×640 | 409,600 | 400 |
| 800×600 | 800×608 | 486,400 | 475 |
| 960×960 | 960×960 | 921,600 | 900 |
| 1280×720 | 1280×704 | 901,120 | 880 |
| 1920×1080 | 1920×1088 | 2,088,960 | 2,040 |
| 3840×2160 (4K) | 2720×1536 | 4,177,920 | 4,080 |
| 4096×4096 | 2048×2048 | 4,194,304 | 4,096 |

- **4K** 는 원본 면적이 `max_pixels` 를 넘기 때문에 **축소**됩니다 (위 표 참고).
- **4096×4096** 은 상한에 걸려 **2048×2048** 로 줄어들고, 토큰은 **상한 4096** 에 도달합니다.

## 여러 장(예: YOLO 크롭 + 저해상도 전체)

이미지마다 위 규칙이 적용되고, **비전 토큰은 보통 합산**됩니다.

| 시나리오 (모두 `vendor`) | 장당 토큰 (근사) | 합계 (이미지만) |
|--------------------------|------------------|-----------------|
| 저해상도 컨텍스트 512×512 1장 | 256 | **256** |
| + 1920×1080 크롭 1장 | 2,040 | **2,296** |
| + 1920×1080 크롭 2장 | 2,040 × 2 | **4,336** |

텍스트·특수 토큰은 별도이므로, **프롬프트 길이**까지 포함한 전체 컨텍스트는 API/로그의 `prompt_tokens` 로 확인하는 것이 정확합니다.

## 직접 재계산하기

```bash
python qwen3_vl_image_tokens.py --width 1920 --height 1080 --preset vendor
```

기본값이 `vendor` 이므로 `--preset` 은 생략 가능합니다.

## 참고

- 극단적인 가로·세로 비 (> 200:1) 는 `smart_resize` 에서 **에러**가 날 수 있습니다.
- HF 로 돌릴 때와 llama.cpp 로 돌릴 때 **`min_pixels` / `max_pixels` 가 다르면** 같은 원본이라도 결과 해상도·토큰이 달라집니다. **벤치마크는 동일 스택**으로 맞추는 것이 좋습니다.
